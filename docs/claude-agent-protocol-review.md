# Agent 前后端协议裁决表

## 使用方式（给审查用的 LLM）

被审查对象：两个 agent 项目的前后端协议设计（Rust daemon 项目、Bun/TypeScript 项目）。
对下方每一条规则，逐条给出：

- **判定**：✅ 符合 / ⚠️ 部分符合 / ❌ 不符合 / ❓ 设计文档未说明
- **证据**：引用设计中对应的具体位置（路由、事件类型、字段名）
- **修改建议**：仅在 ⚠️ 或 ❌ 时给出，越具体越好

每条规则标注了优先级：**P0** 必须满足，**P1** 强烈建议，**P2** 可选优化。
最后按 P0 → P1 → P2 汇总所有非 ✅ 项。

## 基本前提（已定，不作为审查对象）

- 传输层：REST（操作与快照）+ SSE（服务端推送）。不引入 WebSocket，除非出现 PTY/语音等高频双向需求。
- 后端是唯一真相源；前端是可随时断开、随时接入的订阅者。
- 前端类型：TUI、WebUI、Electron、WinUI 等，全部是同构的协议客户端，业务逻辑在后端。

## A. Daemon + 多前端

| # | 规则 | 优先级 | 通过标准 |
|---|------|--------|----------|
| A1 | agent 运行与前端连接完全解耦 | P0 | 所有前端断开后，进行中的 turn（含工具执行）继续跑完并落日志 |
| A2 | daemon 独立于任何 TUI 存活 | P0 | 第一个 TUI 退出不杀 daemon；后续前端可重新接入；有明确的退出方式（`stop` 命令或空闲超时） |
| A3 | TUI 能发现或拉起 daemon | P1 | 启动时先探测（端口文件 / unix socket / lockfile）；不存在则 detached 拉起；防止重复启动多个 daemon |
| A4 | 多前端订阅同一 session 互不干扰 | P0 | 订阅者之间无状态耦合；新前端加入不影响已连接前端 |
| A5 | 抢占类操作有明确规则 | P0 | 工具审批、中断等：先响应者生效，后端广播 `resolved` 事件，其他前端自动关闭弹窗；重复提交返回明确的冲突结果而非报错崩溃 |
| A6 | 待处理状态属于 session 状态而非瞬时事件 | P0 | `waiting_approval` 等出现在快照里；晚接入的前端能看到待审批项 |
| A7 | 慢前端不能拖垮后端 | P0 | 每个订阅者有界队列；超限则断开该订阅者让其走重连，绝不阻塞 agent loop |
| A8 | 本机访问有鉴权 | P1 | 启动生成 token，存放于权限受限文件；防止其他本地进程乱连 |
| A9 | 前端不持有业务逻辑和密钥 | P0 | provider API key、上游原始响应只在后端；前端只认自己协议的事件 |
| A10 | 多 session 并行互相隔离 | P0 | 每个 session 独立的运行任务、事件日志、`seq`；一个 session 出错或卡住不影响其他 |

## B. 断线重连

| # | 规则 | 优先级 | 通过标准 |
|---|------|--------|----------|
| B1 | 每个事件带 session 内单调递增的 `seq` | P0 | 由后端分配，前端只按 `seq` 排序，不用到达顺序或时间戳排序 |
| B2 | 事件先落日志再推送 | P0 | 推给前端的事件一定已写入日志，保证补发和推送内容一致 |
| B3 | 支持按 `seq` 补发 | P0 | 重连时带各 session 的 `lastSeq`，后端补发缺失部分后切换为实时 |
| B4 | 多 session 场景下 `lastSeq` 的传递方式可行 | P1 | 单条汇总流下，原生 `Last-Event-ID` 只有一个值，需用 query 参数或握手请求传 `{sessionId: lastSeq}` 映射；设计里必须说明具体做法 |
| B5 | 日志保留窗口外有降级路径 | P0 | `lastSeq` 太旧时返回"需重新拉快照"信号；前端拉快照后从快照的 `lastSeq` 继续 |
| B6 | 快照与增量无缝衔接 | P0 | 快照带 `lastSeq`；订阅从 `lastSeq+1` 开始；前端按 `seq` 去重；中间不丢、不重复应用 |
| B7 | 进行中的流式消息能续看 | P0 | 快照包含"正在生成的那条消息已累积内容"；接上后续 delta 不缺字、不重复 |
| B8 | 日志持久化 | P1 | 落盘（jsonl / sqlite）；daemon 重启后能恢复历史和 session 列表；重启时对"运行中"的 session 有明确处理（标记中断或恢复） |
| B9 | 前端有自动重连策略 | P1 | 指数退避 + 抖动；重连期间界面有明确的连接状态；重连成功后自动补齐 |
| B10 | 心跳与死连接检测 | P1 | SSE 定期发送心跳注释或事件；前端超时未收到则主动重连 |
| B11 | 操作请求的幂等性 | P1 | 发消息、审批等 POST 携带客户端生成的请求 id；断线重试不会重复执行 |

## C. 协议简化

| # | 规则 | 优先级 | 通过标准 |
|---|------|--------|----------|
| C1 | 不按事件类型拆多条流 | P0 | 消息、工具、状态变化在同一条有序流中，用 `type` 字段区分；不再有独立的 tools / messages / history 流 |
| C2 | 历史不是流 | P0 | 历史通过快照/分页接口获取；SSE 只负责增量 |
| C3 | 统一事件信封 | P0 | 所有事件形如 `{sessionId, seq, type, ts, payload}`；新增事件类型不需要新增连接或路由 |
| C4 | 连接数与 session 数无关 | P0 | 多 session 使用一条汇总流（事件带 `sessionId`），或前端只订阅活跃 session；不会触碰浏览器同域 6 连接上限 |
| C5 | 操作走 REST，不模拟双向协议 | P1 | 发消息、中断、审批用普通 POST；不引入自定义的请求/响应关联机制 |
| C6 | 关联字段完整 | P0 | 工具事件通过 `tool_call_id` 关联开始/结果；更新已有块而非新建；文本块和工具块有稳定 id，`seq` 决定块的先后 |
| C7 | 内容以块为渲染单位 | P0 | 一个 turn 内是 `文本块 → 工具块 → 文本块…` 的有序序列，而不是"一条 assistant 消息 + 附属工具数组"（后者是顺序错位的主要来源） |
| C8 | 后端归一化上游 provider | P0 | 各 provider 的 SSE 在后端翻译为统一内部事件（text_delta / tool_call_delta / finish / usage / error）；前端不见原始上游格式 |
| C9 | delta 合并 | P2 | 后端将过密的 delta 合并为约 30–50ms 一个事件，减轻前端渲染压力；首字节仍立即转发 |
| C10 | 协议有版本号 | P1 | 握手或快照中带协议版本；前端遇到未知 `type` 时忽略而不崩溃 |
| C11 | 两个后端共用同一份协议 | P1 | Rust 与 Bun 的事件 schema、路由、错误格式一致；有单一的 schema 文档作为准则 |

## D. 上下文分页与前端快速渲染

| # | 规则 | 优先级 | 通过标准 |
|---|------|--------|----------|
| D1 | 首屏只加载最新一段 | P0 | 进入 session 时快照只返回最近 N 条块（或按 token/字节预算），而非全量历史 |
| D2 | 向前翻页用游标而非页码 | P0 | 如 `GET /sessions/:id/history?before=<seq>&limit=N`；返回中带 `hasMore` 与下一个游标；新消息到来不会使分页错位 |
| D3 | 分页与 `seq` 体系一致 | P0 | 页内块保持 `seq` 有序；旧页插入到头部时，前端按 `seq` 合并，不与实时增量冲突 |
| D4 | 渲染优先级：先新后旧 | P0 | 先渲染最新部分并可交互；旧历史在滚动接近顶部时懒加载，或在空闲时后台预取 |
| D5 | 向上加载不跳动 | P1 | 插入旧内容后保持滚动锚点（用锚点块或高度补偿）；避免视口跳动 |
| D6 | 大内容截断与按需展开 | P1 | 超长工具输出、大文件内容在快照/历史中只带摘要与大小，展开时通过单独接口获取（如 `GET /sessions/:id/blocks/:id`） |
| D7 | 前端虚拟化列表 | P1 | 长会话只渲染可视区附近的块；折叠的工具块不渲染内部详情 |
| D8 | 内存上限 | P1 | 前端对已加载页有淘汰策略，或明确限制；后端内存中只保留近期日志窗口，其余读盘 |
| D9 | 后端分页读取高效 | P1 | 日志按 `seq` 建立索引或偏移；`before=<seq>` 查询不需要全文件扫描 |
| D10 | 模型上下文与展示历史分离 | P1 | 发给模型的上下文（可能被压缩/截断/摘要）与前端展示的完整历史是两套概念；压缩事件（如 `context.compacted`）在协议中可见，前端能标记"此前内容已被压缩" |
| D11 | 后台 session 降级推送 | P2 | 前端没有在看的 session 只推状态变化（完成 / 等审批 / 出错），不推 delta；切换到该 session 时用快照 + 补发追上 |

## E. 输出格式：汇总报告

请以如下结构输出：

1. **总体结论**（2–3 句）：这套设计是否可以直接实现，最大的风险是什么。
2. **逐项判定表**：按 A / B / C / D 分组，列出编号、判定、证据、建议。
3. **P0 缺陷清单**：所有 P0 中非 ✅ 的项，附修改方案。
4. **P1 / P2 建议**：按收益排序。
5. **设计文档未说明的点**：所有 ❓ 项，需要设计者补充。
6. **两个项目的差异**：Rust 与 Bun 设计在协议上不一致的地方，以及建议统一到哪一边。

判定原则：

- 只依据设计文档和代码中可验证的内容判定；不要臆测未提供的部分，未提供则标 ❓。
- 不要因为"更先进"而建议引入 WebSocket、JSON-RPC 或其他传输，除非能指出当前设计有哪条 P0 规则无法在 REST + SSE 下满足。
- 建议要能落到具体的路由、字段或事件类型上，避免泛泛而谈。
